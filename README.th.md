# maw-rustfs (ภาษาไทย)

[English → README.md](README.md)

ปลั๊กอิน maw แบบอ่านอย่างเดียว สำหรับคนที่รัน RustFS หลายเครื่องและ replicate ข้อมูลระหว่างกัน

```bash
maw rustfs status              # ทุกเครื่องขึ้นอยู่ไหม, latency, จำนวนไฟล์, พื้นที่
maw rustfs repl m5 [bucket]    # rule, ปลายทาง online ไหม, ดับนานเท่าไร, คิว, สรุปหนึ่งบรรทัด
maw rustfs who [port]          # ใครติดตั้ง RustFS เครื่องนี้ จาก repo ไหน เมื่อไร
```

วิธีติดตั้งและตั้งค่าอยู่ใน [README.md](README.md)

## Replication ของ RustFS ทำงานยังไง — ผลที่วัดจริง

> เขียนโดย Nexus (AI) ตัวเลขทุกตัวมาจากคำสั่งที่รันจริงบน m5 วันที่ 2026-09-28
> ใช้ RustFS `1.0.1-preview.11` (Homebrew, macOS arm64) สองตัวบนเครื่องเดียว
> "m5" (ต้นทาง) ที่ `127.0.0.1:29600` และ "black" (สำเนา) ที่ `127.0.0.1:29700` เปิด versioning ทั้งสองฝั่ง

### ภาพรวมแบบเข้าใจง่าย

ให้นึกว่า **m5 คือตู้เอกสารหลัก** และ **black คือตู้สำรอง** ทุกครั้งที่ใส่เอกสารลง m5 ระบบจะถ่ายสำเนาไปใส่ black ให้เองอัตโนมัติ

ผลของอุบัติเหตุต่างๆ ขึ้นกับ **สวิตช์ตัวเดียว** ใน rule คือ "ให้ส่งการลบไปที่ black ด้วยไหม"

- **เปิด** → m5 ลบอะไร black ลบตาม black เป็นแค่ **กระจกเงา (mirror)**
- **ปิด** → m5 ลบอะไร black ไม่ลบตาม black เป็น **ของสำรองจริง (backup)**

> **Replication ไม่ใช่ backup** ถ้าเปิดส่งการลบ มันคือกระจกเงา ความผิดพลาดใน m5 จะลามไปถึง black ภายในไม่กี่วินาที

### ผลที่ 1 — ถ้า black ดับ

| สถานการณ์ | ผลที่วัดได้ |
|---|---|
| ปิด black (`kill -9`) แล้วเขียนไฟล์ 300 KB × 20 ลง m5 | เขียนสำเร็จทุกไฟล์ (ครั้งละ ~0.2 วินาที) ไฟล์ถูกติดสถานะ `FAILED` อ่านจาก m5 ได้ปกติ |
| ลบไฟล์ใน m5 ตอน black ดับ | m5 รับคำสั่งลบปกติ |
| เปิด black กลับมา | **ตามทันเองโดยไม่ต้องทำอะไร**: 0/20 ที่ 15 วินาที, 20/20 ภายใน 30 วินาที ข้อมูลตรงทุก byte และการลบก็ตามไปด้วย |

### ผลที่ 2 — ถ้า black มีการเปลี่ยนแปลงของตัวเอง

| สถานการณ์ | ผลที่วัดได้ |
|---|---|
| เขียนไฟล์ใหม่ลง black อย่างเดียว (rule ทางเดียว) | **ไม่ถูกคัดลอกกลับมา m5** และไม่โผล่ในรายการไฟล์ของ m5 แต่ขอไฟล์จาก m5 แล้วได้ (200) เพราะ m5 ไปดึงจาก black ให้ (proxy read) พอ black ดับก็ได้ 404 |
| black แก้ไฟล์ที่ได้มาจาก m5 | m5 ไม่ได้รับผลกระทบ สองฝั่งไม่ตรงกันจนกว่า m5 จะเขียนไฟล์นั้นใหม่ ตอนนั้นเวอร์ชันของ m5 ชนะ ส่วนที่ black แก้ไว้เก็บเป็นเวอร์ชันเก่า |
| black ลบไฟล์เอง | m5 ยังมีไฟล์อยู่ |
| ตั้ง rule สองทาง (เพิ่ม black → m5) | ไฟล์ใหม่จากฝั่งไหนก็ไปถึงอีกฝั่งภายใน 5 วินาที สำเนาติดสถานะ `REPLICA` ไม่มีการส่งวนไปมา (มี 1 เวอร์ชัน) |
| สองฝั่งแก้ไฟล์เดียวกันตอนขาดการเชื่อมต่อ (m5 เขียนก่อน black เขียนหลัง 5 วินาที) | พอต่อกลับ ทั้งสองฝั่งใช้ **อันที่เขียนทีหลัง** อีกอันเก็บเป็นเวอร์ชันเก่าทั้งสองฝั่ง |

### ผลที่ 3 — ถ้าเผลอลบใน m5 (คำถามหลัก)

ทดสอบกับ bucket ใหม่สองอัน แต่ละอันมีไฟล์ 100 KB × 5 ไฟล์
`vault-del` = **เปิด** ส่งการลบ (`--replicate delete,delete-marker,existing-objects`)
`vault-keep` = **ปิด** ส่งการลบ (`--replicate existing-objects`)

| เผลอทำอะไรใน m5 | เปิดส่งการลบ (mirror) | ปิดส่งการลบ (backup) |
|---|---|---|
| **ลบธรรมดา** (แปะป้ายลบ) | black ซ่อนไฟล์ตาม (404) แต่ไฟล์ยังอยู่ข้างใต้ ดึงป้ายออกแล้ว **ได้คืนครบ** | black **ยังมีไฟล์** (200) ✅ |
| **ลบถาวร** (`DELETE ?versionId=`) | black **หายด้วย กู้ไม่ได้** ทั้งสองฝั่งเหลือ 0 เวอร์ชัน ❌ | black **ยังมีไฟล์** ✅ |
| **ลบทั้ง bucket แบบบังคับ** (`rc bucket remove --force`) | black **ถูกล้างว่างเปล่า** 0 เวอร์ชันทั้งสองฝั่ง คำสั่งจบด้วย error `Concurrent writes left objects…` แต่ไฟล์ข้างในถูกลบไปแล้วทั้งสองฝั่ง ❌ | bucket ใน m5 หายไป แต่ black **ยังเก็บครบ 5 เวอร์ชัน** ✅ |
| **ดิสก์ m5 พัง** (ล้างโฟลเดอร์ข้อมูลทิ้ง แล้วเปิดเครื่องใหม่แบบว่างเปล่า) | – | black **ไม่เป็นอะไร** กู้กลับด้วย `rc mirror black/vault-keep m5/vault-keep` ใช้ 0.99 วินาที ครบ 5/5 ตรงทุก byte รวมถึง 2 ไฟล์ที่ m5 เคยลบไปก่อนหน้า ✅ |

ข้อควรรู้: `rc mirror` กู้ได้เฉพาะ **เวอร์ชันล่าสุด** ของแต่ละไฟล์ ประวัติเก่าใน black ไม่ตามกลับมา

### m5 ตัวจริงตอนนี้ (อ่านด้วย `maw rustfs repl m5`)

- `discord-archive` → ส่งเฉพาะ `raw/` กับ `lance/` ไป kvmlab1 แบบ **ปิดส่งการลบ** ✅ ถ้าเผลอลบใน m5 kvmlab1 ยังเก็บไว้
- `relic-v21` (60 GB) → rule **ถูกปิดอยู่** และไม่มีปลายทาง ⚠️ ไม่มีสำรองที่ไหนเลย ถ้าดิสก์ m5 พัง ข้อมูลก้อนนี้หายหมด

### ถ้าจะตั้ง black.local แนะนำ

1. ส่งไป black แบบ **ปิดส่งการลบ** (ไม่ใส่ `delete` และ `delete-marker`)
2. เปิด **versioning** ที่ black ไว้เสมอ
3. ถ้าอยากชัวร์ขึ้น เปิด **Object Lock** ที่ black (ยังไม่ได้ทดสอบ)
4. แก้หรือเปิด rule ของ `relic-v21` ถ้าข้อมูลนี้สำคัญ
5. เปิด NTP ทั้งสองเครื่อง เพราะ "ใครเขียนทีหลัง" ตัดสินจากนาฬิกาของแต่ละเครื่อง

### ข้อควรระวังตอนตั้งค่า

- RustFS ไม่ยอมให้ปลายทางเป็น `127.0.0.1` (error: `loopback address`) ต้องเปิดเครื่องต้นทางด้วย `RUSTFS_REPLICATION_ALLOW_LOOPBACK_TARGET=true` ส่วนที่อยู่ในวง LAN (เช่น black.local ที่ 192.168.x) เอกสารของ RustFS บอกว่าใช้ได้เลย ตัวแปร `RUSTFS_OUTBOUND_ALLOW_ORIGINS` ใช้กับ replication **ไม่ได้**
- ต้องเปิด versioning ทั้งสองฝั่ง
- ตัวนับ "failed total" เป็นแบบสะสม ขึ้น 20 ค้างไว้ทั้งที่ 20 ไฟล์ส่งสำเร็จแล้ว และตัวนับทั้งหมดรีเซ็ตเมื่อเซิร์ฟเวอร์รีสตาร์ต

### ยังไม่ได้ทดสอบ

- ปลายทางดับเป็นชั่วโมง พร้อมไฟล์หลายพันไฟล์
- รีสตาร์ตต้นทางตอนปลายทางยังดับ (คิวไฟล์ที่ส่งไม่สำเร็จจะรอดไหม)
- นาฬิกาสองเครื่องไม่ตรงกัน
- Object Lock

## อภิธานศัพท์ (Glossary)

### พื้นฐาน

| คำ | ความหมาย |
|---|---|
| **Object** | ไฟล์หนึ่งไฟล์ในระบบ เรียกด้วยชื่อที่เรียกว่า **key** เช่น `raw/2026-09-28/img1.jpg` |
| **Bucket** | ถังใหญ่สุดที่ใส่ object เช่น `discord-archive` |
| **Prefix** | ส่วนหน้าของชื่อไฟล์ ใช้เหมือนโฟลเดอร์ย่อย เช่น `raw/` |

### Replication

| คำ | ความหมาย |
|---|---|
| **Replication** | ใส่ไฟล์ลงเครื่องหนึ่ง ระบบคัดลอกไปอีกเครื่องให้อัตโนมัติ |
| **Source (ต้นทาง)** | เครื่องที่เราเขียนไฟล์ลงไป เช่น m5 |
| **Target / Replica (ปลายทาง / สำเนา)** | เครื่องที่รับสำเนา เช่น black.local, kvmlab1 |
| **Rule** | คำสั่งว่าจะสำเนาอะไร ไปที่ไหน แบบไหน |
| **One-way / Two-way** | ทางเดียว: ของใหม่ในปลายทางไม่ย้อนกลับ / สองทาง: ตั้ง rule ทั้งสองฝั่ง |
| **Existing-objects replication** | ตอนเพิ่งตั้ง rule ให้ส่งไฟล์เก่าที่มีอยู่แล้วไปด้วย ไม่ใช่แค่ไฟล์ใหม่ |

สถานะของแต่ละไฟล์:

| สถานะ | ความหมาย |
|---|---|
| `PENDING` | รอส่ง |
| `COMPLETED` | ส่งถึงปลายทางแล้ว |
| `FAILED` | ส่งไม่สำเร็จ เช่นปลายทางดับ ระบบจะลองส่งใหม่เอง |
| `REPLICA` | ไฟล์นี้เป็นสำเนาที่รับมาจากอีกเครื่อง |

### Versioning และการลบ

| คำ | ความหมาย |
|---|---|
| **Versioning** | ระบบไม่ทิ้งไฟล์เก่าเวลาแก้หรือลบ ทุกครั้งที่เขียนทับได้เวอร์ชันใหม่ ของเก่ายังอยู่ |
| **Version ID** | รหัสประจำแต่ละเวอร์ชัน เช่น `ecf7dd24-fb3d-...` |
| **Delete marker** | **ลบธรรมดา**: แปะป้าย "ลบแล้ว" ทับไว้ ไฟล์ยังอยู่ข้างใต้ ดึงป้ายออกก็กู้คืนได้ |
| **Permanent delete** | **ลบถาวร**: ลบโดยระบุ Version ID ทำลายเวอร์ชันนั้นทิ้งจริง กู้ไม่ได้ |
| **Force delete bucket** | ลบทั้งถัง: ลบถาวรทุกไฟล์ทุกเวอร์ชันก่อน แล้วค่อยลบถัง อันตรายที่สุด |
| **Delete-marker replication** | ส่ง "ป้ายลบแล้ว" ไปปลายทางด้วย |
| **Delete replication** | ส่ง "การลบถาวร" ไปปลายทางด้วย ปลายทางทำลายไฟล์ตาม |
| **Mirror** | เปิดส่งการลบ ปลายทางเหมือนต้นทางทุกอย่าง รวมถึงความผิดพลาด |
| **Backup** | ปิดส่งการลบ ปลายทางเก็บทุกอย่างไว้ ต่อให้ต้นทางลบไปแล้ว |

### อื่นๆ

| คำ | ความหมาย |
|---|---|
| **Proxy read** | ขอไฟล์จาก m5 แต่ m5 ไม่มี m5 เลยไปขอจาก black มาส่งให้ ไฟล์ไม่ได้ถูกเก็บลง m5 จริง |
| **Last-writer-wins** | สองเครื่องแก้ไฟล์เดียวกัน ระบบเลือกอันที่เขียนล่าสุด อีกอันเก็บเป็นเวอร์ชันเก่า |
| **NTP** | บริการตั้งนาฬิกาเครื่องให้ตรงเวลามาตรฐาน |
| **`rc mirror`** | คำสั่งคัดลอกทั้ง bucket จากเครื่องหนึ่งไปอีกเครื่อง ได้เฉพาะเวอร์ชันล่าสุด |
| **Object Lock** | ล็อกไม่ให้ลบถาวรภายใน N วัน เหมาะกับเครื่องสำรอง |
| **MRF (Most Recent Failures)** | คิวไฟล์ที่ส่งไม่สำเร็จ RustFS ลองส่งใหม่เองเมื่อปลายทางกลับมา |
